# UNIT-05 マスタメンテナンス - Functional Design 計画

## ユニットスコープ（前提確認）

対応要件: FR-4.1〜FR-4.8（テーブル/ビュー一覧、レコード一覧、絞込・SQL入力検索、レコード編集・一括反映、レコード作成・削除）
対応コンポーネント: COMP-13 MasterDataService
対応ストーリー: STORY-4.1, STORY-4.2, STORY-4.3, STORY-4.4
前提ユニット: UNIT-01〜UNIT-04（実効権限判定=`EffectivePermissionResolver`、スキーマ情報=`SchemaIntrospectionService`に依存）

既存の決定事項（requirements.md §5.2/§5.4、UNIT-04実装済み）:
- 主権限は3値（`NONE`/`READ`/`UPDATE`）、階層はカラム＞テーブル＞スキーマ（FR-2.4、`EffectivePermissionResolver.resolvePrimary`）
- レコード作成可否: `CREATE`補助権限があり、かつ（主キーなし、または全主キー列が`UPDATE`以上）（FR-2.6、`canCreate`）
- レコード削除可否: `DELETE`補助権限があり、かつ主キーを持ち、かつ全主キー列が`READ`以上（FR-2.7、`canDelete`）。主キーなしテーブルは常に削除不可
- 実効権限判定はUNIT-04時点でAPI非公開（Java直接呼び出しのみ）。本ユニットのバックエンドから同一プロセス内で直接利用する
- スキーマ情報はUNIT-03の`SchemaIntrospectionService`が保持（`SchemaSnapshot`/`SchemaTable`/`SchemaColumn`、`TableType.TABLE`/`VIEW`区別あり）
- 対応RDBMS: MySQL / MariaDB / PostgreSQL / H2（複数方言、`RdbmsDialectStrategy`既存）

### Question 1（Domain Model・重要な設計上の注意点）
「アクセス可能なテーブル/ビュー」（STORY-4.1の一覧表示対象）の判定基準は？

A) そのテーブル配下に主権限`READ`以上のカラムが1つでも存在すれば一覧に表示する（テーブル単位の主権限設定がある場合はそれも含めて階層優先順位どおりに判定）

B) テーブル単位の主権限設定が`READ`以上の場合のみ表示する（カラム単位の設定は一覧表示可否に影響しない）

C) Other（[Answer]: の後に内容を記述）

[Answer]: A

### Question 2（Domain Model）
`VIEW`（`TableType.VIEW`）はマスタメンテナンス機能の対象に含めますか？

A) 含める。ただし常に読み取り専用として扱い、編集・作成・削除は一切不可とする（DBによっては更新可能なビューもあるが、本機能では区別せず一律読み取り専用とする）

B) 含めない（`TABLE`のみを一覧・操作対象とする）

C) Other（[Answer]: の後に内容を記述）

[Answer]: A

### Question 3（Business Rules・重要な曖昧点）
主キーを持たないテーブルは、FR-2.7により削除は常に不可ですが、**更新**（レコード編集・一括反映）はどう扱いますか？行の一意な識別ができないため、更新対象行の特定方法が課題になります。

A) 更新も不可とする（主キーなしテーブルは常に読み取り専用。作成のみFR-2.6の条件次第で可）

B) 更新は許可し、対象行の識別に「取得時点の全カラム値の完全一致」をWHERE条件として使う（同一内容の重複行がある場合は複数行が同時に更新される可能性を許容する）

C) Other（[Answer]: の後に内容を記述）

[Answer]: A

### Question 4（Data Flow・セキュリティ上重要）
STORY-4.2のSQL入力（WHERE句・ORDER BY句の手入力、権限に関係なく実行可）は、どう安全に取り込みますか？直接文字列連結はSQLインジェクションの重大なリスクがあります。

A) 入力されたWHERE/ORDER BY句をSQL構文として構文解析し、許可された構文要素（比較演算子・AND/OR・カラム参照・リテラル値・ORDER BYのカラム＋ASC/DESC等）のみで構成されているかを検証したうえで、パラメータ化した形で組み立て直す（危険な構文＝サブクエリ・関数呼び出し・コメント記号等は拒否）

B) そのまま対象RDBMSへ送るSQLの一部として文字列連結する（NFR-4.3「動的SQL生成部分は特に重点対応」との整合が必要。危険なため要検討）

C) Other（[Answer]: の後に内容を記述）

[Answer]: A

### Question 5（Business Rules）
絞り込みUI（STORY-4.2、フィルタUI）で各カラムに対して使用可能な比較演算子は、カラムのデータ型によって変えますか？

B) 全カラム共通で`=`のみとする（シンプルさ優先）

C) Other（[Answer]: の後に内容を記述）

### Question 6（Business Logic Modeling・重要な曖昧点）
STORY-4.3「一括反映」の統一API（FR-4.8）は、1リクエストでどのような操作の組み合わせを扱いますか？

B) 更新・作成・削除を明確に別々のAPIエンドポイントとして分離する（FR-4.8「単一のAPIエンドポイントに統合」の要件と矛盾するため非推奨だが選択肢として提示）

C) Other（[Answer]: の後に内容を記述）

### Question 7（Error Handling）
FR-4.6「バッチ中の1件でも権限チェックまたは制約チェックに失敗する場合、DBへの変更をゼロ件とする」について、失敗時のレスポンスはどの粒度で失敗理由を返しますか？

A) 失敗した行（バッチ内のインデックスまたは主キー値）と失敗理由（権限不足／制約違反／値不正等）を配列で返す。フロントエンドはこれを使い該当行にエラー表示する

B) バッチ全体として単一のエラーメッセージのみ返す（どの行が失敗したかは特定しない）

[Answer]: A

### Question 9（Domain Model）
